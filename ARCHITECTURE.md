# ZV67 — архитектура системы

**Статус:** проект архитектуры, реализация не начата.  
**Платформа:** macOS, Apple Silicon.  
**Рабочая директория:** `/Users/orfeev/Desktop/Projects/ZV67`

## 1. Назначение

ZV67 — локальный шлюз для использования Google Search AI Mode через существующий OpenCodeX в Codex Desktop и Codex CLI.

Система должна обеспечивать:

1. Подключение нескольких Google-аккаунтов.
2. Управление авторизацией и сессиями.
3. Распределение запросов между аккаунтами.
4. OpenAI-совместимый API.
5. Экспериментальную поддержку Responses API и агентских вызовов.
6. Регистрацию модели в OpenCodeX.
7. Веб-панель управления и статистики.
8. Локальную установку, автозапуск, обновления и диагностику.
9. Публикацию собственного кода в приватном GitHub-репозитории.

Целевая схема:

    Codex Desktop / CLI
             |
             v
          OpenCodeX
             |
             v
        ZV67 Gateway
             |
       +-----+------+
       |            |
    Agent API   Management API
       |            |
       |        Web Dashboard
       |
    Session Manager
       |
    Request Router
       |
    Account Manager
       |
       v
    Google AI Mode

CLIProxyAPI используется для других задач и не входит в эту цепочку.

## 2. Принципы архитектуры

### Простая реализация полного продукта

Выбран модульный монолит: один локальный backend, отдельная сборка frontend, одна SQLite-база.

Не требуются Redis, Kubernetes, Docker, RabbitMQ или отдельный сервер.

Компоненты должны иметь явные интерфейсы и независимые тесты.

### Проверяемые возможности

Нельзя объявлять функцию работающей только потому, что для неё создан endpoint или элемент интерфейса.

Для каждой возможности предусмотрены статусы:

- VERIFIED — подтверждена тестами.
- EXPERIMENTAL — работает частично или нестабильно.
- UNSUPPORTED — технически не поддерживается.
- NOT TESTED — проверка не выполнена.

### Независимость от внешнего протокола

Протокол Google AI Mode неофициальный и может измениться.

Весь код обращения к нему изолируется в отдельном адаптере. Остальные компоненты не зависят от HTML, cookies или внутренней структуры ответов Google.

### Сохранность окружения

ZV67 не изменяет CLIProxyAPI и другие действующие сервисы.

Конфигурации Codex и OpenCodeX изменяются только на отдельном этапе интеграции после проверки и резервного копирования.

## 5. HTTP API

Основные маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | /health | Состояние сервиса |
| GET | /v1/models | Зарегистрированные модели |
| POST | /v1/chat/completions | Chat Completions |
| POST | /v1/responses | Responses API |
| GET | /admin | Панель управления |
| * | /admin/api/* | Management API |

По умолчанию сервер слушает только `127.0.0.1`.

Рабочий порт определяется конфигурацией. Предпочтительный порт — `18080`, если он свободен.

### Внутренняя модель запроса

Нормализованный запрос содержит:

- request_id;
- session_id;
- model_id;
- сообщения и их роли;
- системные инструкции;
- определения инструментов;
- параметры генерации;
- streaming flag;
- идентификатор выбранного аккаунта, если задан;
- параметры отмены и таймаутов.

Общий формат отделяет API клиентов от Google backend.

### Responses API

Реализуются реальные используемые клиентом структуры:

- input/output;
- сообщения с ролями;
- response IDs;
- function_call;
- function_call_output;
- streaming events;
- completion/error events;
- отмена запроса.

Поддерживаемая версия протокола определяется после исследования установленного Codex/OpenCodeX.

Сервер не должен возвращать фиктивные успешные tool calls.

Неподдерживаемые возможности возвращают явную ошибку.

## 6. Google AI Mode Backend

Вводится интерфейс `UpstreamProvider`.

Он должен поддерживать:

- проверку доступности;
- отправку запроса;
- получение ответа;
- продолжение диалога;
- потоковый вывод при наличии поддержки;
- обработку ошибок;
- отмену;
- идентификацию внешней сессии.

Предусмотрены две реализации.

### Mock Provider

Полностью локальный детерминированный провайдер.

Используется для разработки и тестирования без реальных Google-аккаунтов.

Не создаёт сетевых соединений с Google.

### Google AI Mode Provider

Реальный адаптер к Google Search AI Mode.

Исследовательская основа:
https://github.com/XD06/google-ai-mode

Исходный код XD06 нельзя копировать без проверки лицензии и соответствующих прав.

Реальный адаптер создаётся после подтверждения доступного протокола, условий использования и технической осуществимости.

Не допускаются обход CAPTCHA, антибот-защиты, ограничений доступа и других защит Google.

При недоступности реального upstream остальные компоненты приложения продолжают работать с mock backend.

## 7. Account Manager

Каждый аккаунт представляется отдельной сущностью.

Поля:

- account_id;
- display_name;
- credential_reference;
- subscription_status;
- enabled;
- connection_status;
- last_success_at;
- last_error;
- concurrency_limit;
- routing_weight;
- active_requests.

Статусы:

- ACTIVE
- DISABLED
- UNAUTHORIZED
- DEGRADED
- COOLDOWN
- UNKNOWN

Функции:

1. Добавление и удаление аккаунтов.
2. Безопасный импорт авторизации.
3. Включение и отключение.
4. Проверка состояния.
5. Настройка веса и параллельности.
6. Просмотр индивидуальной статистики.

Аккаунты изолированы по credentials, истории и сессиям.

Статус Google AI Pro отображается только при наличии проверенного источника данных. Иначе — «Неизвестен».

## 8. Request Router

Поддерживаемые стратегии:

- Round-robin.
- Weighted round-robin.
- Least-busy.
- Manual selection.
- Sticky sessions.

По умолчанию используется Round-robin для новых диалогов с закреплением аккаунта на протяжении сессии.

Выбор аккаунта и получение права на выполнение запроса должны быть атомарными.

Router контролирует:

- максимальную параллельность;
- очередь;
- занятость аккаунтов;
- timeout;
- Retry-After;
- cooldown;
- состояние подключений.

Существующую сессию нельзя незаметно перенести на другой аккаунт.

Перенос допускается только при полном восстановлении контекста, отсутствии повторных побочных действий и соблюдении ограничений upstream.

## 9. Session Manager

Session Manager сохраняет:

- локальный session_id;
- идентификатор аккаунта;
- внешний Google thread ID;
- историю сообщений;
- состояние агентского цикла;
- идентификаторы вызовов инструментов;
- время создания и последней активности.

Основные инварианты:

1. Один диалог закреплён за одним аккаунтом.
2. Результат инструмента относится к конкретному tool_call_id.
3. Повторный запрос не должен повторно выполнять завершённое действие.
4. Контекст разных аккаунтов не смешивается.
5. Завершение процесса не повреждает сохранённую сессию.

История диалога, если её хранение требуется, сохраняется зашифрованной с ограниченным сроком жизни. Обычный журнал запросов не содержит промптов и исходного кода.

## 10. Agent Tool Adapter

Главная экспериментальная часть системы.

Задача — преобразовывать ответы Google AI Mode в структурированные вызовы инструментов Codex.

Целевой цикл:

    User request
         |
         v
    AI Mode reasoning
         |
         v
    Structured tool call
         |
         v
    Codex executes tool
         |
         v
    Tool result
         |
         v
    AI Mode continues

Поддерживаются:

- определения доступных инструментов;
- JSON Schema для аргументов;
- строгая валидация ответов;
- связь call_id с результатом;
- несколько шагов агента;
- лимит шагов;
- обработка ошибок;
- отмена и завершение.

ZV67 не выполняет shell-команды и не изменяет файлы проекта напрямую на основании текстового ответа модели.

Исполнение инструментов остаётся на стороне Codex, с его разрешениями и sandbox.

Если AI Mode не способен надёжно создавать структурированные вызовы, агентский режим остаётся EXPERIMENTAL или UNSUPPORTED.

Системные инструкции, встроенные в пользовательский текст, не равнозначны нативной поддержке system/developer roles.

Нельзя считать текстовую имитацию tool calling доказательством полноценной агентской совместимости.

## 11. Интеграция с OpenCodeX

Новый provider:

    Provider ID: zv67
    Model ID: google-ai-mode
    Display name: Google AI Mode (ZV67)

API endpoint:

    http://127.0.0.1:18080/v1

Точный формат конфигурации зависит от установленной версии OpenCodeX.

Целевые сценарии:

1. OpenCodeX обнаруживает provider.
2. Модель отображается в списке.
3. Chat-запрос проходит через ZV67.
4. Codex CLI использует модель.
5. Проверена возможность выбора в Codex Desktop.
6. Остальные модели продолжают работать.

Появление модели в `/v1/models` само по себе не доказывает её доступность в интерфейсе Codex Desktop.

Если нативный селектор не поддерживает стороннюю модель, необходимо документировать и проверить поддерживаемый способ переключения через OpenCodeX.

Конфигурации действующих сервисов сохраняются.

- количество запросов;
- количество успешных запросов;
- HTTP-коды ошибок;
- задержка;
- p50/p95;
- time to first token;
- число активных запросов;
- число вызовов инструментов;
- распределение по моделям;
- распределение по аккаунтам.

Каждый запрос фиксируется один раз с уникальным request_id.

Повторные попытки учитываются отдельно.

Точная токенная статистика показывается только при наличии достоверного источника.

Оценки токенов должны быть помечены как приблизительные.

Остатки квот Google AI Pro не выдумываются.

Если Google не предоставляет достоверный остаток, отображается «Нет данных».

## 16. Management API

Management API отделён от клиентского AI API.

Требуется:

- авторизация администратора;
- безопасное хранение пароля;
- защита изменяющих операций;
- защита от CSRF;
- защита от XSS;
- ограничение попыток входа;
- проверка входных данных;
- отсутствие секретов в ответах;
- журнал административных действий.

Cookie авторизации должен использовать HttpOnly и SameSite. Атрибут Secure обязателен при HTTPS; для локального HTTP конфигурация должна учитывать реальное поведение браузера.

По умолчанию внешний сетевой доступ отключён.

## 17. Безопасность

Основные правила:

1. API доступен только через localhost по умолчанию.
2. Секреты изолированы от исходного кода.
3. Google credentials хранятся в защищённом виде.
4. Административный API имеет отдельную авторизацию.
5. Входные данные строго валидируются.
6. Предусмотрена защита от SSRF, CSRF, XSS и path traversal.
7. Команды Codex исполняются только через стандартную инфраструктуру Codex.
8. Повторные запросы не дублируют побочные эффекты.
9. Перед публикацией проверяется отсутствие секретов.
10. Удаление аккаунта предусматривает удаление его credentials и связанных защищённых данных.

Диагностические логи не содержат cookies, паролей, API-ключей, содержимого файлов и полных промптов по умолчанию.

## 21. Границы текущего этапа

На архитектурном этапе не выполняются:

- установка зависимостей;
- системные настройки;
- Google login;
- импорт cookies;
- изменение Codex/OpenCodeX;
- изменение CLIProxyAPI;
- Git commits/push;
- публикация файлов;
- изменение данных вне ZV67.

Следующие этапы определены в `docs/IMPLEMENTATION_PLAN.md`.
