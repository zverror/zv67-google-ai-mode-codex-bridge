# ZV67 — план реализации

**Статус:** запланировано.  
**Основа:** `ARCHITECTURE.md`.  
**Цель:** полноценное локальное приложение ZV67, а не демонстрационный прототип.

## 1. Правила выполнения

1. Реализовывать систему последовательно, сохраняя полный согласованный объём.
2. Каждый этап должен давать проверяемый результат.
3. Существующие приложения и конфигурации сохраняются.
4. Неподтверждённые возможности обозначаются явно.
5. Результаты тестов нельзя придумывать.
6. Не переносить код XD06 без проверки прав.
7. Не использовать реальные Google credentials в автоматических тестах.
8. Не выполнять внешние действия без соответствующего разрешения.

Документация проекта пишется на русском языке. Комментарии в коде — на английском.

На текущем этапе разрешена работа только с файлами проекта ZV67.

Установка, диагностика системы, интеграция с установленными приложениями, GitHub-публикация и реальные тесты выполняются отдельно Codex в рамках соответствующих разрешений.

## 3. G0 — исследование и проверка осуществимости

До реализации реального Google backend Codex должен проверить:

- исходники и лицензию XD06;
- доступные публичные интерфейсы;
- ограничения использования Google AI Mode;
- фактический формат диалогов;
- требования к авторизации;
- возможности streaming;
- особенности сохранения контекста.

Также отдельно исследуются:

- установленная версия OpenCodeX;
- формат custom providers;
- протокол запросов Codex;
- формат Responses API;
- механизм выбора моделей в Codex Desktop.

**Результат:** `docs/FEASIBILITY.md`.

Документ должен различать:

- подтверждённые факты;
- предположения;
- неподтверждённые возможности;
- технические ограничения;
- юридические ограничения.

Критерий: ни одно неподтверждённое свойство Google не принимается как гарантированная возможность.

## 4. T01 — Backend Foundation

Создать минимальное работающее ядро будущей системы.

Реализовать:

- Python package;
- конфигурационную модель;
- FastAPI application factory;
- доменные структуры запросов и ответов;
- интерфейс UpstreamProvider;
- Mock Provider;
- health endpoint;
- models endpoint;
- базовый Chat Completions;
- обработку ошибок;
- первоначальные тесты.

Mock Provider должен быть детерминированным и не обращаться в интернет.

Отдельный идентификатор тестовой модели:

    zv67-mock

Не выдавать mock за Google AI Mode.

Создать основу для дальнейшего подключения настоящего backend без переписывания API.

**Приёмка:**

- backend импортируется;
- тестовый сервер создаётся;
- `/health` возвращает корректное состояние;
- `/v1/models` возвращает mock-модель;
- Chat Completions корректно обрабатывает тестовый запрос;
- неподдерживаемые функции возвращают явную ошибку;
- отсутствуют внешние сетевые запросы.

Пока тесты не выполнены, их статус — NOT TESTED.

## 6. T03 — Account Manager & Router

Реализовать управление несколькими аккаунтами.

Функции:

- add;
- list;
- status;
- enable;
- disable;
- remove;
- health check;
- account concurrency;
- routing weight;
- cooldown.

Маршрутизация:

- round-robin;
- weighted round-robin;
- least-busy;
- manual selection;
- sticky sessions.

Использовать атомарную выдачу request lease.

**Приёмка:**

- запросы распределяются предсказуемо;
- отключённый аккаунт не выбирается;
- concurrency limit соблюдается;
- при 429 применяется Retry-After;
- cooldown соблюдается;
- разные аккаунты не получают чужие credentials;
- сессия закрепляется за своим аккаунтом.

Первоначально тестировать только на mock accounts.

## 7. T04 — Session Manager

Реализовать:

- локальные session IDs;

- привязку к аккаунтам;
- внешние thread IDs;
- TTL;

- учёт tool call IDs;
- безопасное завершение;
- контроль повторных операций.

История содержимого должна храниться защищённо.

**Приёмка:**

- связанный диалог сохраняет историю;
- рестарт не повреждает сессию;
- аккаунты изолированы;
- результаты инструментов относятся к правильным вызовам;
- повторный запрос не дублирует завершённое действие;
- удаление сессии удаляет связанные защищённые данные.

## 9. T06 — Google AI Mode Backend

После G0 реализовать настоящий upstream.

Функции:

- ручная авторизация поддерживаемым способом;
- изоляция аккаунтов;
- запрос;
- продолжение диалога;
- получение ответа;
- обработка ошибок;
- управление соединением;
- закрытие ресурсов.

Весь специфичный код Google должен оставаться внутри backend adapter.

Не выполнять обход защит Google.

Не копировать XD06 без соответствующих прав.

**Приёмка:**

- один реальный запрос успешно обработан;
- ответ соответствует отображаемому в AI Mode;
- продолжение диалога проверено;
- ошибки различаются;
- аккаунты изолированы;
- секреты не раскрываются.

При отсутствии авторизованного аккаунта:

**LIVE: NOT TESTED.**

## 10. T07 — Agent Tool Adapter

Реализовать преобразование между агентским протоколом Codex и доступными возможностями AI Mode.

Обязательные функции:

- строгая JSON Schema;
- реестр разрешённых инструментов;
- сопоставление call_id;
- передача результатов;
- многошаговый цикл;
- ограничение количества шагов;
- timeout;
- cancellation;
- обработка ошибочных инструкций;
- защита от повторного исполнения.

Не исполнять команды напрямую в Gateway.

Не использовать другую LLM для скрытой генерации решений.

**Приёмка на mock:**

- структурированный tool call корректно формируется;
- невалидный вызов отклоняется;
- результат относится к исходному call_id;
- цикл корректно завершается;
- дублирующее выполнение предотвращается.

**Live agent acceptance:**

1. Модель запрашивает чтение файлов.
2. Модель инициирует изменение тестового файла.
3. Модель анализирует ошибку теста.
4. Модель исправляет код.
5. Модель проверяет результат.

Каждый шаг должен подтверждаться трассировкой.

Если live-проверка не пройдена, агентская возможность не объявляется VERIFIED.

## 18. Журнал доказательств

Создать `docs/VERIFICATION.md` на этапе тестирования.

Для каждого теста фиксировать:

- идентификатор;
- дату;
- версию ZV67;
- используемый backend;
- команду или сценарий;
- ожидаемый результат;
- фактический результат;
- ссылку на безопасный лог;
- статус;
- причину ограничения.

Mock PASS не считается Live PASS.

Не смешивать тесты адаптера с подтверждением настоящих возможностей Google AI Mode.

## 19. Контроль завершённости

Проект готов к полноценной эксплуатации только после прохождения всех обязательных gates.

Если отдельная внешняя возможность технически недоступна, приложение может выпускаться с документированным ограничением, но статус соответствующей функции остаётся UNSUPPORTED или EXPERIMENTAL.

Нельзя объявлять полноценную агентскую интеграцию реализованной, если AI Mode не прошёл реальный агентский сценарий.

Нельзя объявлять интеграцию с Codex Desktop успешной без проверки выбора модели и выполнения запроса.
